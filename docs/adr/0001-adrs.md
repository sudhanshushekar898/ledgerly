# Architecture Decision Records

## ADR-001 Modular monolith, not microservices
**Context:** The first sketch had 4 services (gateway, user, wallet, notification), each with its own database. There is one team, one domain, and transfers need ACID across user wallets.
**Decision:** Single Spring Boot app, modules with ArchUnit-enforced boundaries, one Postgres.
**Consequences:** No sagas, simple deploy, strong consistency. Splitting later is possible because modules talk via facades and events. Revisit only with a measured scaling or team-ownership need.

## ADR-002 Double-entry ledger with cached balance
**Decision:** Immutable journal entries are the source of truth; `account.balance` is updated in the same transaction. DB CHECK prevents negative user balances; trigger forbids entry mutation. Reconciliation verifies both.
**Alternative rejected:** balance-only column (no audit trail, cannot prove correctness).

## ADR-003 Pessimistic locking in fixed order for balance changes
**Decision:** `SELECT ... FOR UPDATE` on both accounts in ascending UUID order.
**Why not optimistic:** hot accounts cause retry storms; ordered locking is deadlock-free and simpler to reason about. `@Version` remains for non-money edits.
**As built:** PostgreSQL does the sort (`ORDER BY id FOR UPDATE`), because `java.util.UUID.compareTo` compares signed longs and does not match PostgreSQL's uuid order. `@Version` is kept on accounts as a second line of defence.
**Lesson found by the concurrency test:** the first version read the wallet as a JPA entity before locking it. Hibernate kept that cached instance, so under contention the lock failed with an optimistic-locking error. Without `@Version`, it would have been a silent lost update. The fix is that read paths return projections (`AccountView`), so no Account entity is in the persistence context when `post()` locks it.
**Known hot spot:** every top-up locks the single `SYSTEM_TOPUP_SOURCE` row, so top-ups are serialised system-wide. The load test later confirmed it and ADR-014 shards it.

## ADR-004 Idempotency-Key on money-moving POSTs
**Decision:** Table `idempotency_record(user_id, key, request_hash, status, response, expires_at)` unique on `(user_id, key)`; written in the same transaction as the transfer. 24h retention.
**As built:** there is no IN_PROGRESS status. The record is claimed with `INSERT ... ON CONFLICT DO NOTHING` in the same transaction as the posting.
- A racing duplicate request blocks on the unique index until the first request commits (then it replays the stored response) or rolls back (then it runs itself).
- A failed request (for example, an invalid amount) leaves no record, so a retry runs again. This is safe because nothing happened the first time.
- Same key with a different body returns 422 `IDEMPOTENCY_KEY_REUSED`. A replay returns the identical body plus `Idempotent-Replayed: true`.
- Not yet built: a scheduled purge of expired records. Today an expired record is deleted only when its key is reused.

## ADR-005 Single currency (INR)
Multi-currency needs FX rates and rounding policy; out of scope.

## ADR-006 Transactional outbox + Kafka, at-least-once with idempotent consumer
**Decision:** Events written to `outbox` in the business transaction; a relay publishes to Kafka using `SKIP LOCKED`; consumers dedupe via `inbox`. Kafka (rather than in-process events) lets new consumers subscribe without touching the payment code, and gives real broker semantics: partitions, keys, acks, consumer groups and a DLT. It is the only broker.
**As built:**
- **Event:** every ledger posting writes exactly one `MoneyMoved` event (payer, payee, amount, kind) to `outbox_events` inside `post()`'s transaction. A rolled-back payment leaves no event (tested). `Outbox.record` is `MANDATORY`, so an event cannot be written outside a transaction.
- **Relay:** polls every 300 ms. It locks a batch with `FOR UPDATE SKIP LOCKED`, sends with `acks=all` and an idempotent producer, and marks a row published only after the broker's ack. It stops at the first failure to keep order. While Kafka is down, events wait in the table (unit-tested with a failing broker).
- **Delivery:** at least once. The relay can resend after a crash, so the `notifications` consumer records each event id in `processed_events` in the same transaction as its notifications. A redelivery is skipped (tested by sending the same event twice).
- **Topic and ordering:** topic `wallet.money-moved` with 3 partitions, keyed by the payee's user id, so each user's events arrive in order.

## ADR-009 as built
- Retries: 3 with exponential backoff (200, 400, 800 ms), then the message is published to `wallet.money-moved.DLT` with Spring Kafka's exception headers.
- Parse failures (`JsonProcessingException`) are not retryable and go straight to the DLT.
- The consumer is a tolerant reader: unknown fields are ignored, so a newer producer cannot poison it.
- Tested: a non-JSON message lands on the DLT, and the next message on the same partition is still processed.
- Monitoring: every parked message increments `notifications_dead_lettered_total`, and the `EventsDeadLettered` alert fires on any increase. The replay procedure is in `docs/RUNBOOK.md`.

## ADR-013 Observability: Micrometer → Prometheus → Grafana, with a continuous reconciliation alarm
**Decision:** the backend exposes `/actuator/prometheus`, with HTTP latency histograms and business metrics.

| Metric | What it tracks |
|---|---|
| `ledger_postings_total{kind}`, `ledger_posted_amount_total{kind}` | money moved, counted only after commit |
| `app_rejections_total{code}` | business rejections by error code |
| `idempotency_replays_total` | retries answered from the idempotency store |
| `outbox_pending`, `outbox_oldest_age_seconds`, `outbox_publish_failures_total` | the outbox backlog and relay failures |
| `notifications_dead_lettered_total`, `notifications_live_streams` | parked messages and open live streams |

**Reconciliation:** a scheduled job reconciles the whole ledger every 60 s (15 s locally) and publishes `ledger_reconciliation_healthy`, `ledger_total_balance` and `ledger_reconciliation_last_run`.

**Alerts:** `LedgerOutOfBalance`, `ReconciliationStale`, `EventsDeadLettered`, `OutboxBacklog`, `HighServerErrorRate` and `SlowApi`, each linked to a runbook section.

**Guardrails:**
- Metrics are doubles, so money becomes a `double` only at the hand-off to Micrometer. ArchUnit's "no floating-point money fields" rule caught a first draft that stored it in a `double` field.
- `/actuator/prometheus` is open inside the compose network but not proxied by Nginx. In production it belongs on a private management port.

**Verified:** adding ₹5 to one wallet by SQL turned the gauge red within one reconciliation run. The alert fired 30 s later, the log named the exact account id, and the alert cleared after the fix.

## ADR-008 Corrections by reversal, never by edit
A refund is a new REVERSAL transaction that links to the original and posts the opposite entries. Each transaction can be reversed at most once (unique constraint). The daily limit is checked under the same row lock as the transfer, so parallel transfers cannot exceed it.
**As built:** one pattern, "check under the lock", is behind both rules.
- **Daily limit:** the transfer is posted first. That locks the sender's row until commit and flushes the new entries. Then today's outgoing total, including this transfer, is summed, and if it's over the limit the whole transaction rolls back. A parallel transfer from the same wallet waits on the lock and then sees the first one, so 10 parallel transfers of 10,000 against a 50,000 limit give exactly 5 successes (tested).
- **Reversal:** "already reversed?" is checked again after the locks are taken. A racing duplicate therefore gets `ALREADY_REVERSED`, not a confusing `INSUFFICIENT_FUNDS`. The unique constraint stays as the final guard (tested with 6 parallel reversals).
- **Freeze:** reversals bypass a freeze on purpose, so money can be clawed back from a frozen fraudster.
- **Money already spent:** a reversal fails with `INSUFFICIENT_FUNDS` if the recipient already spent the money. Wallets never go negative, so recovering that money is a manual operations task (out of scope).
- **Limit after a refund:** a reversed transfer still counts toward the sender's daily limit. This is conservative: refunds don't restore the limit.
- **Lesson:** a `default` interface method that calls the `@Transactional` overload bypasses the Spring proxy (self-invocation) and runs with no transaction. `LedgerIT` caught it, so both overloads are now real `@Transactional` methods.

## ADR-009 Consumer retries and dead-letter topic
3 retries with exponential backoff, then publish to `wallet.transfers.DLT` with the error reason. The DLT count is a metric with an alert. A runbook explains how to replay messages.

## ADR-010 One Idempotency-Key per payment attempt in the client
**Context:** server-side idempotency only helps if the client resends the *same* key when it retries.
**Decision:** each payment form keeps one key per attempt.
- It is generated on the first submit.
- It is kept after any failure, so a timeout followed by "Send" again is a replay.
- It is replaced when a field changes (a different payment) or after a success.
- Payments are never retried automatically: the person decides, and the key makes deciding safe.
- The API client's refresh-and-replay after a 401 resends the same key.

**Consequence:** a double submit or a network blip cannot double-charge, and the UI can honestly say "press again, it's safe". Tested with a mocked network failure: both requests carry the same key, and editing the amount produces a new one.
**Refined:** the key is tied to the payment's *content* (recipient, amount, note), not to "has a field been touched". Going back from the review step and paying again unchanged therefore keeps the key: that is still the same payment, so it must not charge twice. Changing any value is a different payment with a new key. The review screen shows the key, so the mechanism is visible.

## ADR-011 Engineering console: API inspector and Resilience Lab in the product UI
**Context:** the guarantees (idempotency, lock ordering, no overdraft) are invisible in a normal UI, so the project looked like CRUD.
**Decision:**
- The client records each API call's metadata in memory: status, latency, request ID, Idempotency-Key, and the replay flag from the `Idempotent-Replayed` header.
- An inspector page shows these calls.
- A Lab page runs three experiments with real requests and checks invariants on the results.
**Guardrails:**
- No bodies or tokens are recorded, and emails in URLs are masked.
- Experiments move small synthetic amounts only to a recipient the user verified.
- Amounts stay within the normal per-payment and daily limits. The Lab has no special server privileges; it is just a client.

**Consequence:** a reviewer can watch "5 requests, 1 executed, 4 replayed" happen live, against the same API customers use.

## ADR-012 Live notifications over server-sent events, read with fetch
**Decision:** the browser keeps one `text/event-stream` connection (`GET /api/v1/notifications/stream`). The consumer pushes a `notification` event after its transaction commits.
- **Why fetch, not EventSource:** the client reads the stream with `fetch()` because `EventSource` cannot send the `Authorization` header. A token in the URL would leak into access logs.
- **Reconnects:** with backoff (1 s up to 30 s), and once more after refreshing an expired token.
- **Keeping the connection open:** a heartbeat comment every 20 s keeps proxies from closing it, and Nginx disables buffering for this one route.

**Why not WebSockets:** traffic is one-way (server to browser). SSE is plain HTTP, works through the existing proxy and auth, and reconnecting is simple.

**Known limit:** open streams live in one instance's memory. With several instances, the instance that consumes an event may not hold the user's connection. The fix when scaling out: a per-instance broadcast consumer group, or Redis pub/sub.

## ADR-014 Shard the top-up source account
**Context:** every top-up debits the one `SYSTEM_TOPUP_SOURCE` row under `FOR UPDATE`, so all top-ups queue behind a single lock. Measured: 136 top-ups/s against 597 transfers/s on the same stack.

**Decision:**
- 8 source accounts (`shard` 0–7, migration V7), unique per `(type, shard)`.
- A user's top-ups always pick `floorMod(userId.hashCode(), shardCount)`, so the mapping is stable and spreads users evenly.
- Shards are ordinary ledger accounts: double entry, the zero-sum invariant and reconciliation cover them unchanged.

**Result:** 368–447 top-ups/s and p99 657 → 325–411 ms (docs/PERFORMANCE.md).

**Trade-off:** "the system's total money in" is now a sum over 8 rows, not one balance.

**Why not other options:**
- *Drop the lock on the system account:* that would break the no-negative-balance and ordering guarantees.
- *Batch top-ups asynchronously:* the customer would no longer see a confirmed balance in the response.

## ADR-015 Pipelined outbox relay
**Context:** the relay awaited each Kafka acknowledgement before sending the next event: 210 events/s, below the 400–600 payments/s the app sustains, so the backlog grew without bound under load.

**Decision:**
- Lock a batch of 500 with `SKIP LOCKED`, hand all of it to the producer, then await every acknowledgement.
- Mark the unbroken prefix of confirmed events published in one JDBC batch.
- Loop immediately while batches are full.

**Still safe:**
- `acks=all` plus the idempotent producer keeps durability and per-partition order.
- Events after a failure are not marked published, so they are sent again; consumer dedup (`processed_events`) makes the resend harmless.

**Result:** ≥ 4,190 events/s drain (~20×); under load the backlog peaked at 759 and returned to 0.

**Trade-off:** a failure mid-batch can resend up to 499 events that Kafka already has. That is acceptable under at-least-once delivery.

## ADR-007 No cloud infrastructure in scope
Cloud infrastructure is out of scope: the project runs as a Docker Compose stack, and a deployment would add infrastructure-as-code and managed PostgreSQL and Kafka.
